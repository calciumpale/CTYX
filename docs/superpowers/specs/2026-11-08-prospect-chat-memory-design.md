# 回复机器人记忆设计

日期：2026-11-08。状态：用户已确认，进入实施。

用户已确认：**每个获客任务单独记忆**。用户于本次会话确认按下文架构、默认值和界面行为实施。

## 1. 要解决什么

让机器人在同一任务内持续理解同一客户：说过的需求不反复问，修改过的需求能更新，隔天继续聊能接上，已经留资或拒绝留资不会被遗忘，人工接待后也能延续已确认的进展。

客户自己的陈述、商铺等产品的客观事实、实际发生的发送和预约动作，分别保留证据。机器人不能把“想周六看铺”说成“已预约成功”，也不能把客户预算当成房源价格。

本轮不增加自动催客、自动外呼、跨任务客户画像共享或新的云端记忆服务。下一步事项先用于接待和人工查看，不因为记住“周六联系”就自动向客户发消息。

用户实施中追加：使用按需决策的 agentic RAG。普通寒暄、沟通方式、需求确认和客户已知需求回顾可以直接回答；需要房源、价格、条件、制度等业务内容时，机器人自行决定检索已授权知识库，把召回内容与本任务记忆一起作为上下文回答。检索不提供依据时不能补写业务事实。

职责进一步确认：agentic RAG 属于知识库公共能力，供工作台其他 Agent 复用。回复机器人识别意图、整理任务内记忆与上下文，再调用知识库；检索规划、授权资料召回、直接回答／证据回答和失败边界都由公共知识库模块执行。普通工作台对话与工作流也接入相同能力，不各自复制一套 RAG。

## 2. 当前情况与已复现的问题

以代码提交 `6be27d1` 为基线：

- D1 已保存 `memory_json`，刷新或助手重启不会自动清空。当前内容是面积、业态、预算、区域、入驻时间、看场六类需求，加上阶段、留资状态与邀请／拒绝次数。
- Store 加载最近 40 条消息，Agent 再缩到最近 12 条。摘要只是六字段拼接；“要一楼、不要转让费、周末才方便”等信息没有稳定的长期承载方式。
- 正常运行时 Store 总会传入规范化记忆对象；Agent 的“没有记忆才回填旧对话”分支因此不会补齐空记忆。

- 邀请次数在回复生成／排队时增加，不代表已经成功发出。
- 当前平台会话按 `owner + sender + recipient` 唯一，不按任务唯一。不能仅增加任务字段就允许两个机器人同时接待同一聊天窗口。

## 4. 身份与任务隔离

### 平台会话

平台会话继续按 `ownerId + senderAccountId + recipientId` 唯一。它负责真实平台消息、可靠快照、外发结果和停止联系状态。昵称只用于显示，不能用于合并客户；更换抖音发送账号也不能复用另一账号的聊天身份。

### 任务接待

任务接待以 `platformThreadId + campaignId` 唯一，同时保存并校验 `ownerId / memberId`。需求、摘要、留资状态、留资拒绝和次数、异议、待办、可供模型读取的历史，都归属于这个接待记录。

同一客户在任务 A、B 中有两份独立记忆，默认不复制、不检索另一任务的内容。成员或任务权限变化后，旧权限不能继续读写记忆。

### 一个聊天窗口只有一个自动接待任务

- 每个平台会话保存唯一 `activeSessionId` 与 `bindingVersion`。创建新任务或匹配到同一客户，不自动抢占原来的接待任务。
- 另一个任务显示“此客户当前由任务 A 接待”，由有权限的用户明确切换。切换前显示将暂停原任务接待。
- 切换时原子更新绑定版本，取消旧任务未开始的 queued／waiting 回复。已经 running 或结果 unknown 时，先核实外发结果，再开放新任务自动接待。
- 新消息按当时的绑定版本归入任务。切换记录保存可靠消息水位；另一任务的旧消息不能重新变成待回复消息，也不能出现在新任务的模型上下文中。
- 无可靠边界、没有明确接待任务或出现归属冲突时，保留消息并暂停自动接待，提示人工指定；不靠模型猜任务。
- **人工接管、停止联系和未知外发保护继续按平台会话生效**，切换任务不能解除这些保护。这是发送控制，不是跨任务共享业务记忆。
- 任务 A 已由人工接管时，切到 B 仍保持人工模式；“切换任务”和“恢复 AI”是两个独立动作。恢复 AI 必须由有权限的用户明确操作，并通过新任务快照、绑定版本与现有发送门禁检查。各任务可保留自己的接待进度，但不能覆盖平台会话的人工接管锁。

## 5. 记什么、如何更新

| 内容 | 保存方式 | 回复时如何使用 |
| --- | --- | --- |
| 当前需求 | 业态、面积、区域、预算及单位／周期、入驻时间、看场意向 | 不重复询问已确认项，按当前有效需求检索业务资料 |
| 附加条件 | 楼层、排烟、转让费、交通等明确条件；明确的排除项 | 记住“必须”和“不要”，不只保存正向偏好 |
| 沟通过程 | 客户已问的问题、已核实提交的回答、未回答问题、异议、沟通偏好 | 优先答当前问题和未解决问题，避免一直收集需求 |
| 接待状态 | 已问／待回答／已拒绝／已撤销；是否留资、已核实提交的邀请次数 | 避免重复问同一个问题，继续遵守留资策略 |
| 下一步事项 | 客户提出的看场意向、销售确认的安排、待人工核实的事项 | 明确区分意向、待确认、已确认、已完成和已过期 |
| 摘要 | 当前有效事实、最近进展、未解决问题与下一步的紧凑投影 | 帮助隔天续聊；可由原始事实与事件重建 |

每条事实至少带：字段／内容、状态、来源消息 ID 和原文片段、陈述者、来源时间、确认时间、版本、被哪条新事实替代。状态为 `confirmed / tentative / retracted / superseded / stale`。

更新规则：

1. 客户明确的新陈述或纠正可以更新原值。“预算改成8000”替代旧预算；“不看滨江”撤销旧区域；“不做餐饮了”撤销旧业态，不能自动猜新业态。
2. 有单位、主体或意思歧义时保存为待确认，不覆盖成确定事实。例如“8000”保留缺少计费周期的状态；“我朋友预算8000”不能成为本人的预算。
3. 保留旧值与来源，当前上下文只使用有效版本。摘要不得把已撤销信息重新写回来。
4. 模型只提交候选变更。服务端检查来源归属、来源片段、字段类型、金额／单位、否定与版本；无证据的推测不进入已确认记忆。消息中的指令不能修改记忆规则或任务权限。
5. 客户的新纠正优先于较早的人工备注。人工修订也保留操作者、原因和证据；冲突无法判断时先核实。
6. “明天”“下个月”保留原文，并以可靠的原消息时间和业务时区解析。时间不可靠时只记待确认；看场日期过期后不能每天向后顺延。
7. 一般需求超过 30 天未确认时标为可能过期，相关时简短核实；不清空全部记忆、不重新问一遍。具体日期事项到期立即改变有效状态。30 天为本稿建议默认值。
8. 联系方式原文继续保留在现有有权限的留资记录中；模型和历史检索上下文只拿已留资状态及脱敏内容。

确认事项的证据分级：客户提出“周六想看铺”只生成意向；可识别的人工销售明确确认了时间与安排，可记为 `sales_confirmed`，机器人只能按人工确认的范围复述，例如“按销售同事确认的周六14点安排”。可核实的系统回执记为 `system_verified`，才允许称系统预约成功。人工记录“已电话联系”可记为人工报告的跟进，不自动推断客户已接听。转述、条件句、含糊措辞或无法可靠识别操作者的外发消息先保留为待核实，不升级为执行完成；不额外要求销售上传附件。

## 6. 每次回复怎样使用记忆

1. 完成现有身份、任务、人工接管、停止联系和未知外发检查，确定唯一的活动接待记录与绑定版本。
2. 对可靠的新消息按任务归属入库；记忆吸收独立于“本轮是否允许机器人发送”。客户在人工接待期间说的新需求，也能进入待核验／已确认记忆。记忆处理水位与 inbound 的回复 processed 状态分开，更新记忆不代表已经回复。
3. 读取当前事实、待解决问题、已核实提交的上一问、摘要、近期消息；根据本轮问题从**当前任务**召回少量较早的原文证据。
4. 先理解新消息中的需求变更，并由服务端核验，形成新的有效事实快照，再做业务资料检索。基础提取可以直接完成明确的变更；需要语义理解时增加一次有界、结构化的记忆提取调用。无法确定的变更先核实，不能一边沿用旧条件查询，一边声称已经改好。
5. 知识库查询带入更新后的相关有效需求。例如“预算改8000，有合适的吗”按已确认的新预算检索；单说“有合适的吗”也带入已确认的区域、面积、预算。回复生成器使用该快照和本轮业务资料，服务端再校验引用的证据；不能直接把模型输出整体写入数据库。
6. 回复优先级是：处理当前问题／纠正 → 补一个确有必要的未知条件 → 适时自愿邀请留资。已留资、拒绝、人工接管等状态继续遵守已有规则。
7. 客户事实、业务资料、外发提交／执行事件使用不同证据标识。允许引用已验证客户事实说“您之前提到……”，但房源、价格、可用性仍必须有业务资料；预约和联系按上节证据分级表达，不把人工报告升级为系统回执。
8. 写入时以 `sessionVersion + bindingVersion + sourceWatermark` 做并发校验。新消息、人工纠正或任务切换出现后，旧模型结果作废，不覆盖新记忆、不排队旧回复。
9. 模型不可用时保留事实和原消息；不把提取失败或摘要失败当成客户没说过。能够依据确定事实回答的简短回顾可用确定性模板，否则说明待核实或转人工。

模型上下文保留时间和陈述者，区分客户、机器人和人工销售。先给当前有效事实与约束，再给摘要、近期对话、相关旧消息和业务资料，避免旧值压过新值。

建议第一版记忆上下文上限：近期最多 20 条且不超过 6000 字符，较早消息最多 5 段，摘要最多 1000 字符，记忆与消息合计不超过 9000 字符；超额先裁剪无关旧消息。安全控制、当前新消息和关键有效事实不被静默裁掉，超出可用模型预算则走明确降级。实际值可由评估调整。

普通回复最多一次主生成，需要语义记忆提取时再增加一次有界调用；不为了省一次调用而用旧需求做检索。无需业务资料的需求回顾／确认，可在一次调用中提出候选记忆和回复，再按先校验记忆、后校验回复的顺序处理。摘要是已验证事实／事件的可重建投影，初版不要求每条消息另调一次摘要模型。历史召回始终先做任务与成员过滤，再排序、限量和脱敏。

Agentic RAG 补充约束：主判断可返回直接回答或 `retrieve(query)`；服务端执行至多一次有界知识检索，再做一次最终回答。明确涉及业务事实时不得绕过知识证据；直接回答只用于不需要业务资料的内容及可核实客户事实。语义记忆提取、检索决策、最终回答合计受 bridge 请求预算约束，分别采用约8秒、8秒、12秒的模型上限，知识召回沿用有界超时。检索失败、空结果和证据冲突必须区分；不会反复检索形成无限循环。记录路线和使用的证据ID，不记录模型内部思维过程或原始联系方式。

记忆吸收由可靠同步完成事件和人工操作触发，幂等登记待处理水位；复用现有服务端轮询处理机会，每次有界处理，不依赖会话必须处于 agent 模式。提取失败保留待处理项，恢复 AI 前要求关键新消息已处理或明确走待核实降级；不能把失败水位标成已完成。具体批次大小和事务拆分留给实施者。

## 7. 把“准备说”与“已经说”分开

消息状态沿用现有发送机制，记忆增加相应事件：

- `drafted / queued / waiting` 只表示准备发出，不写成“已询问／已告知”。待发送提问可阻止重复排队。
- 当前 `sent` 对应 bridge 的 `outcome=submitted`，只证明已在已核对的会话中观察到外发提交，不能称已送达或已读。记忆使用 `submitted_verified` 事件，记录已提交的提问／告知和留资邀请次数；不新增未经平台支持的送达状态。
- 确认提交前失败，不消耗已提交次数；重试属于同一个逻辑提问，不能累计两次。
- `unknown` 保留为待核对，不能当作没发过重发，也不能当作已核实提交继续推进。
- 客户拒绝留资立即成为当前任务的持久状态。客户明确要求停止联系，仍立即进入平台会话级停止联系状态。
- 人工接待中的客户陈述与人工已发送消息可更新相应事实／事件；人工接管只改变谁回复，不关闭记忆吸收。恢复 AI 接待前先建立截至最新可靠水位的记忆快照。

留资文案与规则保留：了解一至两项关键需求后适时邀请，主动文案为“方便留一个可联系到您的方式吗？”。拒绝后不再主动索取；客户明确重新提出联系请求时按既有最多两次邀请策略处理。收到有效本人联系方式后回复“收到，我们会尽快与您联系。”。停联、人工接管和敏感问题优先。

## 8. 界面与人工纠错

扩展现有对话里的“客户需求”区域为“本任务记忆”，无需另建一个管理系统：

- 默认显示当前有效需求、最近进展、未解决问题和下一步；待确认、可能过期与已确认分开显示。
- 每项可以查看来源消息、记录时间与变更历史，并跳回当前任务中的来源消息。
- 提供“纠正”“标记不再适用”“忽略这条记忆”；操作保留审计记录，并使正在生成的旧回复失效。
- “忽略”保存抑制标记，摘要和旧历史召回不能再次从同一来源学回来。模型历史中相关来源片段也要过滤／脱敏；客户之后明确重新提供的新信息可以另建事实。
- 显示当前自动接待任务。任务切换入口说明消息归属边界和正在核对的发送状态。
- 留资次数显示“邀请已提交 N 次”，另列待发送、待核对或无法核实的旧记录；不显示为已送达。

本轮先设计以上行为，不在设计确认前改线上页面或制作完整界面。

## 9. 持久化、迁移与兼容

建议复用原平台会话 ID 和消息主记录，新增任务接待与记忆表；旧 ID 已进入 job 和本机 journal，不能直接重建或改变其哈希。

| 数据 | 最小职责 |
| --- | --- |
| task sessions | 平台会话／任务／合法成员关联、状态、版本、消息水位；唯一 thread＋campaign |
| message attribution | 消息归属接待、绑定版本；平台消息只保存一次 |
| memory facts | 带来源、状态和版本的事实及替代关系 |
| memory events | 需求变更、客户问题、已核实提交的提问、异议、下一步和人工纠错等事件 |
| memory snapshot | 当前有效事实 ID、待办、摘要、摘要覆盖水位、schemaVersion；支持重建 |

具体表名、索引和迁移编号留给实施计划确定。读取快照按 session 定位；事实和历史召回索引必须包含任务／接待及水位，禁止无界扫描全部历史。所有新写入携带合法任务、成员和平台身份校验。

迁移规则：

1. 为旧平台会话建立其原 campaign 的接待记录；无法确定归属的旧消息只保留平台原始记录，先不喂给模型。新任务不会继承旧任务记忆。
2. 按有界批次回填当前任务已有可靠历史。旧 flat 记忆作为迁移输入，有来源才能标为已确认，无法核实的保留为历史待核实。
3. 回填只建立新记忆，不创建回复、不重新处理历史 inbound、不修改已审核／已发送状态、不重算发送额度，不清理本机 journal。
4. 用稳定来源 ID 和水位幂等回填；并发新消息或人工修改不能被旧批次覆盖。已有留资、留资拒绝、人工接管和平台停联状态必须保留。缺少来源的旧拒绝仍作为该任务的邀约抑制，不能因为降为待核实而恢复主动索取。
5. 旧邀请次数单列为迁移前已用的保守邀约预算，不冒充已核实提交次数；迁移后的新邀请只能消耗原有剩余预算，回填旧消息不再重复扣减，也不能自动归零或返还预算。只有可核实的记录纠正或已有规则允许的客户主动重新联系，才按相同上限调整，不因换任务或关闭灰度解除旧任务的保护。
6. 兼容期投影 `memory.needs / stage / contactCaptured / contactDeclines / contactAsks`，其中旧版次数字段承担保守发送门禁，界面另用真实事件计数。关闭新生成策略仍保留任务归属、人工接管、停联、未知外发与邀约抑制；不能回到把各任务内容混合的上下文。二进制回退若尚不能兼容新归属，先停止自动接待，不静默按旧任务继续回复。
7. 留资关联也按 session 读取；不得因为平台会话或线索池中有任务 A 的联系方式，就把任务 B 标成已留资。旧留资记录 ID 保留兼容，B 只有在自己的可靠消息或人工录入提供证据后才能建立本任务关联；任务切换不自动改变负责人或复制联系方式。
8. 字段忽略／更正必须同时影响当前事实、摘要、旧历史召回；不能仅清空显示文本。原始消息保留政策沿用现有产品，永久删除不属于本次默认动作。

## 10. 验收与实施边界

以离线合成对话和真实 SQLite／隔离浏览器夹具验证，不向真实客户发送测试消息。

| 场景 | 必须满足 |
| --- | --- |
| 同任务隔天、刷新、助手重启后续聊 | 保留需求与进展，不重新问已确认字段 |
| 超过 12 条对话后提到旧条件 | 能召回“一楼／不要转让费”等相关条件及来源 |
| 预算与区域一起改口 | 更新正确字段，旧值不再参与查询，保留变更史 |
| 否定旧业态但未给新业态 | 撤销旧值，必要时只问新的用途 |
| 客户问自己以前说过的面积 | 准确复述；客户事实无需冒充业务资料 |
| 数字无单位／第三方信息／模糊指代 | 不推断为本人的已确认需求，必要时追问 |
| “明天看铺”跨天、日期过期 | 使用原始日期锚点；不能说已预约或自动顺延 |
| 邀请排队后失败、重试或 unknown | 计数与已核实提交一致，不冒称送达、不重复邀请／外发 |
| 已留资、拒绝留资、要求停联 | 分别保留正确任务状态和平台级停止联系保护 |
| 人工接待后恢复 AI | 记住人工期间客户的新需求与已确认进展，不抢答 |
| 人工接管 A 时切换到 B | 保持人工控制，明确恢复 AI 后才允许新任务接待 |
| 旧拒绝／邀请次数缺少来源并关闭灰度 | 保留保守抑制，不归零后再次主动索取 |
| 人工明确确认、客户意向、系统回执 | 分级表达，不混淆人工确认与系统预约成功 |
| 同客户不同任务 | 业务记忆与模型历史不串用，同一窗口只一个任务自动接待 |
| 切任务时旧回复正在生成／待发送 | 旧版本不能入队；running／unknown 先核实 |
| 旧历史回填重复或与新消息并发 | 记忆幂等，不回放旧回复、不覆盖新事实 |
| 纠正、忽略记忆后继续聊 | 错误值不会从摘要或旧历史再次冒出来 |
| 模型提取／摘要失败、超预算 | 原消息与有效事实保留，降级可见，不静默遗忘 |
| 客户说了预算或看场意向 | 不能据此生成房源事实、价格承诺或预约成功 |

评估分别记录：事实提取／纠正是否准确、已知字段重复追问率、跨任务污染、外发提交状态是否准确、回顾回答能否找到来源、延迟与模型调用量。日志只记录 ID、版本、水位和错误类别，默认不记录联系方式原文。

实施顺序建议：先修复已复现的提取与客户事实引用，再完成平台会话／任务接待分层、事实与事件持久化、人工接待吸收和历史回填，最后接界面与端到端验收。完整实施计划应在用户确认本稿后编写；迁移和发送安全约束不能因先修局部问题而绕过。

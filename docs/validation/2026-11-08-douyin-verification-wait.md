# 账号核验等待与发送结果

## 现场证据

本机日志中的多次失败带有 `ACCOUNT_VERIFICATION_PENDING`、`retryable: true`，且没有发送检查点；后续独立尝试确实提交成功。网页会话也显示这些失败气泡之后的已提交回复。旧流程把核验等待记录成业务发送失败，又重新生成回复，造成重复气泡、额外模型调用和回复额度消耗。

## 修复边界

- 同一逻辑回复保留一个消息 ID、正文和气泡；执行尝试使用不同任务 ID，保留完整审计记录。
- 只有严格确认发生在发送前的账号核验等待允许自动恢复。发送已开始、已提交或结果未知均不自动重发。
- 自动重试最多两次，冷却分别至少一分钟、五分钟；耗尽后显式同步可授权额外一次，仍不绕过冷却与可靠快照。
- 新来信、外发、快照或策略变化、人工接管、暂停、断开与停止联系都会撤销旧待发回复。旧完成上报不能修改新的尝试。
- 未发送的等待不占回复额度；发送间隔、租约、账号、收件人、租户与策略检查保留。等待不重复运行模型或更新同一来信的记忆。
- 本人页使用一个有界期限等待控件与账号信息稳定；短暂控件替换或重复相同标签不会立即判失败。重复标签本身不能授权发送，身份冲突、登录和安全验证仍阻断。
- 诊断仅保存固定原因枚举，不记录页面文本、账号信息或密钥。
- 旧 AI 核验等待移入可展开记录。真正失败、结果未知和人工显式重试继续保留。

## 验证

专项回归使用隔离数据库与浏览器页面；没有向客户发送合成测试消息。

最终全套带浏览器测试：1082 通过，0 失败，0 跳过。类型检查、72 文件 token 检查与 diff 检查通过。独立复查发现并关闭延迟重试回读产生第二气泡，以及旧等待历史阻塞后续新来信恢复两项问题；未知发送、同文歧义、人工接管与跨租户约束保留。

桌面与手机界面已经检查：等待状态原位变为提交状态，旧 AI 核验记录可展开，人工显式重试与真实失败仍可用；草稿、输入法、阅读位置与 36/44px 控件规范保留。

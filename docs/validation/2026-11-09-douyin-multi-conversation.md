# 多联系人会话同步与回复修复

日期：2026-11-09。本文记录代码与隔离验证；安装、发布及真实会话恢复结果另以发布后的诊断为准。

## 现场与根因

- 本机助手保持在线、账号已核验，安装的四个桥接核心文件与修复前仓库一致。
- 目标主页属于 A，但抖音保留着 B 的可见聊天面板。旧 `openConversation` 只在没有面板时点击主页私信按钮，因此不会选回 A；后续目标核验正确地拒绝了错人面板。
- 目标核验只保存一个绑定和一个全局冷却时间。正常 A、B、A 轮询需要各自的新名片证明，却会受另一个联系人的核验冷却阻塞。A 的一次失败还会暂时压住 B 的正确读取。
- 另一个活动获客任务的 `chatEnabled` 为关闭。活动任务并不等于开启会话同步；后端按所有已启用任务轮转，未启用的任务不会自动入队。用户已明确授权在修复后开启该任务的同步与自动回复。
- 该任务的最新来信在关闭期间已手动同步，因观察模式保留为 `eligible=0`。同次读取也将原招呼的本地 `greeting:` 键关联成抖音消息键。旧逻辑按前缀查找招呼，开启或显式恢复后均未能重获当前来信的时序证明。

## 修改

- 导航后清除会话选择记录；已有面板但尚未选定目标时，使用该主页唯一可见的原生私信入口选择目标，再核验真实名片。选择记录本身不能授权读取或发送。
- 每个收件人维护独立的核验尝试预算。成功后换文档、换联系人再返回时重新核验；失败仍保留该收件人的冷却，不影响其他人，也不能靠切换联系人清除失败预算。
- 缓存仍绑定页面、浏览器上下文、目标、名片节点、签名、快照和有效期。读取仍比较核验前后快照，发送仍独立核验账号与目标并执行持久化发送检查点。
- 关闭转开启时，在同一数据库事务记录恢复意图，覆盖已观察到的未处理来信，以及当前接待任务匹配且有效的排队、执行中观察读取。旧读取仍为观察模式；后续自动可靠读取才可恢复未答来信。任务或身份不同、过期、人工接管、已关闭、退订或外发结果未定的会话不据此自动回复。
- 已完成的同一任务发送记录保留身份和原生消息键证明，键改名后也能用于时序核实。只允许当前任务中经可靠快照证明的最新未答来信恢复，历史 `eligible=0` 记录不会成为其他消息的锚点。
- 新增五项实际 Chromium 回归并注册到全量测试：旧面板选择、A/B/A 轮询、失败隔离、失败预算保留、A/B 各自读取和回复。合成发送仅写隔离页面数组，不访问真实平台或账号。
